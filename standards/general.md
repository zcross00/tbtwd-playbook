# Coding Standards — General

These principles apply to all code in all projects, regardless of language. Language-specific files in this directory add rules on top of these.

---

## 1. Naming

**Clarity over brevity.** A name should answer "what is this?" without needing the surrounding context.

- Use the full word unless the abbreviation is universally known in the domain (`id`, `url`, `http`, `json` are fine; `cnt`, `tmp`, `val` are not).
- Names that include "Manager", "Handler", "Util", or "Helper" are a design smell — they often mean the responsibility isn't clearly defined. Find a noun that names the concept.
- Booleans should read as a question: `isComplete`, `hasChildren`, `canQueue`.
- Don't encode the type in the name: `characterList` → `characters`; `stringName` → `name`.

---

## 2. Size and Focus

**Each unit of code (method, class, module) should do one thing.**

- A method longer than ~30 lines is usually doing more than one thing. Extract.
- A class that references more than ~5 other types is usually doing more than one thing. Split.
- If naming a method requires "and" (e.g., `validateAndSave()`), it is doing two things. Separate them.

---

## 3. Magic Values

**No unexplained literals in logic.**

Bad:
```java
if (familiarity < 0.3) { ... }
roll += 8;
```

Good:
```java
if (familiarity < HOSTILITY_THRESHOLD) { ... }
roll += MAX_SHELTER_BONUS;
```

Constants belong at class scope (or in a dedicated constants class/enum) with a name that states *why* the value exists, not just what it is.

---

## 4. No comments

**Code carries no comments.** Not the what, not the why. The code says what it does through its names, types and structure, and reads one way only. The reasoning behind it (decisions, constraints, workarounds, trade-offs) lives in the project's design docs, which name the code they explain.

*Why:* the owner (2026-11-02): "We want to adjust standards to ban all code comments. All comments and justification should live in designs, but the code should explain itself, with no alternative interpretations". A comment is a second account of the code that nothing checks. When the two drift, a reader has two readings and no way to tell which is true. One account in the code, and one place for the why, leaves nothing to drift.

### What counts as a comment

Anything in a code file that the compiler or interpreter ignores, or that exists only to be read by people:

- line and block comments: `//`, `/* */`, `#`, `<# #>`, `--`;
- doc comments: Rust `///` and `//!`, Javadoc and C# XML docs, Python docstrings;
- a string used as a comment, such as a bare string statement in Python;
- commented-out code;
- `TODO`, `FIXME`, `HACK` and the like.

"Code file" means source, scripts, build files, CI workflows, and config and data files a tool parses (TOML, YAML, RON and the like). Markdown and other docs are not code: that is where the why goes.

### What to do instead

| You would have written | Do this |
|---|---|
| A comment saying what a block does | Extract the block into a function whose name says it |
| A comment on what a value means | A named constant, a newtype or an enum ([§3](#3-magic-values)) |
| A comment on why it's done this way | A design doc entry that names the function or type and gives the reason |
| A comment on a workaround for an outside bug | A function named for the workaround, and its design doc entry links the upstream issue |
| A `TODO` | A `parked` issue ([Tracking work](../playbook/03-tracking.md)) |
| Commented-out code | Delete it. Git has it |
| `// Given`, `// When`, `// Then` in a test | Blank lines between the parts; a long setup becomes a helper named for what it sets up. The test's name states the behavior ([§8](#8-tests)) |
| A doc comment on a public function | A name and types that say it. Where outside consumers need reference docs, they go in a docs page, not the source |
| An explanation of a config key | The key's entry in the doc that documents that config |

A design doc names code by its path and item (`sim/src/economy/converse.rs`, `fn pick_topic`), never by line number, so the name is the link. When code is renamed, its design entry is renamed in the same PR.

### Edge cases

These are decided, so nobody has to interpret the rule:

1. **Generated code is exempt.** A file written by a tool (a generator's output, bindings, a lockfile) is listed by path in the project's `.playbook.toml` under `[comments] exempt`, and may keep whatever header the generator writes, such as "Generated by X; edit X, not this file". The generator's own source follows this rule. *Why:* nobody reads or edits that file by hand, and the header stops someone hand-editing it.
2. **Vendored third-party code is exempt** the same way, by path. We don't edit what we don't own, so its comments, and any license header it legally requires, stay.
3. **No license headers in our own files.** The repository's `LICENSE` covers every file in it. If a project ever needs a per-file notice for legal reasons, that is the owner's call and is added to the exempt list by path, not written into each file.
4. **Lint allow attributes are code, and are allowed.** `#[allow(...)]`, `#[expect(...)]`, `@SuppressWarnings`, `[SuppressMessage]` and `#pragma warning disable` are read by a tool, so they aren't comments. They carry no justification: no comment beside them and no `reason = "..."` text, because a reason string is a comment by another name. Prefer fixing what the lint flags; where an allow stays and the reason isn't obvious, the reason goes in the design doc.
5. **Tool directives that can only be written as comments are allowed**, as the directive alone with no words after it: a shebang (`#!/usr/bin/env bash`), an encoding line, `# noqa: E402`, `# type: ignore`, `# pragma: no cover`, `# fmt: off`, `# shellcheck disable=SC2086`, `# yaml-language-server: $schema=...`, `#Requires -Version 7`, `// eslint-disable-next-line rule`, `// @ts-expect-error`. Anything else in that comment is a comment.
6. **Doc comments are comments.** `///`, `//!`, `/** */`, XML docs and docstrings are banned like any other. A project with no outside consumers (a game, an app, internal tools) has no one reading rendered API docs. A library published for others documents its API in a docs page, from the names and types.
7. **Unsafe code carries no `// SAFETY:` comment.** The unsafe block goes in a small function whose name states what it relies on, and the safety argument goes in the design doc entry for that function.
8. **User-facing text, log messages, `--help` output and error messages are not comments.** They are output. They are not a place to hide reasoning either: a string nothing prints is a comment.
9. **Markdown examples of code are docs**, not code. Examples in the standards still don't model comments that would be banned in real code.

### Enforcement

The kit's comment check, `kit/lint/comments.py` ([kit/README.md](../kit/README.md)), finds comments in every code file the project tracks, honoring the exempt list and the directives above.

- **New code:** `comments.py --diff origin/main` lists comments on lines a PR adds or changes. Each work thread runs it before marking a PR ready, and Code review runs it on every train head. A comment it lists is a change request, like a failing test.
- **Existing code:** comments already on `main` when this rule took effect are removed by a planned sweep, one groomed issue per file or small group of files, scheduled around active work, with any real reasoning moved into the design docs first. `comments.py --count` shows what's left, largest file first. A line a PR touches loses its comment in that PR, since the check counts it as added.

## 5. Validate at Boundaries, Trust Internally

**Validate data when it enters the system. Trust it once inside.**

- Validate at system entry points: user input, file reads, network responses, external APIs.
- Do not add defensive null/range checks inside internal code called only from other internal code you control. The caller is responsible for passing valid data.
- If you find yourself adding `if (x == null)` deep inside a domain method, the real problem is that null is being passed at all — fix the caller or the design.

---

## 6. Immutability

**Prefer immutable data where feasible.**

- Objects that represent a snapshot or value — and don't need to change after creation — should be immutable.
- Expose mutable collections only when the caller genuinely owns the mutation. Otherwise return unmodifiable views or copies.
- Avoid setters unless the mutation is the explicit purpose of the method.

---

## 7. Error Handling

**Fail fast; don't swallow errors silently.**

- Unexpected states should throw, not silently return null or default values. A hiding failure is harder to debug than a loud one.
- Only catch exceptions you can meaningfully handle at that call site. Let others propagate.
- Don't use exceptions for control flow. If something is a normal optional outcome (not found, not applicable), model it in the return type.

---

## 8. Tests

**Tests document expected behavior; they are also the first user of your API.**

- Name tests as sentences: `playerCannotQueueSameActionTypeTwiceInOneDay()`, not `testQueue2()`.
- One assertion concept per test. A test that asserts five things can only tell you *something* failed, not *what*.
- Tests should not depend on execution order. Each test sets up its own state.
- Don't test implementation details — test observable behavior. If renaming a private method breaks a test, the test is testing the wrong thing.

---

## 9. Abstraction Level

**Don't abstract until you have two different uses for the same thing.**

- Helpers and utilities created for one call site are premature. Write it inline; extract when the second use appears.
- Don't design for hypothetical future requirements. Build for what is needed now.
- When a simpler solution and a clever solution both solve the problem, choose simple.

---

## 10. Code Review Mindset

When reviewing (or generating) code, ask:

- Would someone unfamiliar with this project understand what this does in under 30 seconds?
- If this breaks at 2am, does the error message or stack trace tell you exactly where and why?
- Does this add complexity that isn't earning its keep?
- Does it read one way only, with no comment to explain it ([§4](#4-no-comments))?
