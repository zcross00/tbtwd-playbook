# 6. CI tiers

The process doesn't depend on how big the CI is. It depends on two gates and one queue. Start at the smallest tier that keeps the merge queue under a few hours, and move up when the measurements say so, not before.

---

## Two gates, at every tier

| Gate | Where | What | Who relies on it |
|------|-------|------|------------------|
| **Ready** | The author's own environment (agent container, dev machine) | The project's full local check (`scripts/ci.sh` or equivalent): format, lint, tests, coverage gates, every headless/integration check | The author, before marking ready and before every push |
| **Merge** | The shared runner(s) | The same full checks on the target platform, on the tree that lands (the train), with `main` merged in | Code review, before merging |

Plus a **nightly** full run on `main`.

Two rules apply at every tier:

- **Docs-only PRs skip the heavy runner.** A cheap job asks whether the PR touches anything but docs; if not, it goes green in seconds.
- **The required check is never skipped or neutral.** Hosts like GitHub count a skipped required check as passing. A job that shouldn't run reports a passing placeholder on a light runner or stays missing.

---

## The tiers

### Tier 0: one laptop

A self-hosted runner on the owner's (or a team member's) machine.

- **Setup:** register the runner per repository (personal accounts can't share runners across repos). Labels: one heavy label (`self-hosted, <os>, <toolchain>`) and one `light` label for small jobs.
- **Queue:** runners take queued jobs in no defined order, so a `queue` job on a queue-only runner holds each run until it's its turn (priority A first, then longest waiting; anything waiting 2 hours counts as A). Nothing is cancelled to jump the line.
- **Light runner:** a separate runner instance for labels, board sync, the docs-only check and placeholder jobs, so they never wait behind a full build.
- **Costs:** free, but it's the throughput limit. On the reference project a six-core laptop ran a full check in about 25–55 minutes, about two merges an hour with trains.
- **Fits:** a solo owner, a prototype, a small team.

### Tier 1: one dedicated build server

The same setup as Tier 0 on a machine that does nothing else, with more cores and memory.

- **Setup:** several heavy runner instances, each with its own build cache / target directory (disk sets the count: a warm cache can be 15–20 GB). Split the full check into parallel jobs (build-and-test, integration checks) so one PR uses two instances and two PRs run at once.
- **Measure first:** if two runs side by side are each more than 1.5× slower than one alone, drop back an instance and keep the split.
- **Fits:** when the queue regularly passes 2 hours, or the owner's machine is needed for other work.

### Tier 2: hosted overflow with a budget

Hosted runners (GitHub-hosted, or a cloud equivalent) used only where they take load off the self-hosted ones.

- **Never on every push.** Hosted jobs run by hand, or through a rule that checks the month's spend first. On the reference project, hosted CI on every push billed ~3,100 minutes in one day before anyone noticed, more than a month's free allowance.
- **Overflow rule:** when two or more ready runs are ahead in the self-hosted line, the next goes to a hosted machine, one at a time, only while `main` is green and the month's spend leaves room for one more run under a soft cap.
- **Budget:** set a monthly cap. Warn at ~75%, stop starting hosted work at ~90%. A daily report reads the bill (minutes and cost) and any day over a threshold goes to the coordinator at once.
- **Equivalence:** the hosted job runs the same steps on the same OS, merging the current `main`, so a green hosted run counts for the merge gate.
- **Other uses:** acceptance/playtest builds, release builds, anything that would otherwise block the queue.

### Tier 3: enterprise CI

A managed pool (autoscaling runners on Kubernetes, a vendor CI, or an internal platform team).

- **Keep the gates and roles; swap the machinery.** The ready gate, the merge gate, trains (most enterprise platforms call this a merge queue), the nightly run and `main-fix` all map directly.
- **Map roles to controls:** Code review's merge authority becomes branch protection with a required merge-queue check and CODEOWNERS for areas; Verification becomes a post-merge acceptance step with its own sign-off; `deferred gate` issues become your risk/waiver register; the decision log becomes your architecture decision records (ADRs).
- **Audit trail:** the `Refs` + evidence-line rule, `Covers:` attestations and quoted decisions give change-management evidence for free. Keep them.
- **Coverage and quality** are gated in the pipeline itself if the host's rulesets can't do it (floors a point under measured, raised in the same PR that raises coverage; lowering a floor needs a `deferred gate` issue).
- **Fits:** several teams, compliance requirements, more than a handful of merges an hour.

## When to move up

| Signal (measured weekly) | Move |
|---|---|
| Median queue wait > 1 h, or worst > 3 h, two weeks running | Tier 0 → Tier 1 |
| Tier 1 saturated and a hardware purchase isn't justified yet | Add Tier 2 overflow under a budget |
| More than one team, required audit, or > ~5 merges/hour sustained | Tier 3 |

Dev process reports queue wait, CI wall time and re-merges per PR every week, so these signals are always on hand.

---

## Time budgets: no run that can't finish

A run that is known to blow its time limit costs a whole run and tells nobody anything. Four rules, at every tier:

- **Never raise a timeout to make a run fit.** A run that grew past its timeout is a run that has to get faster or smaller. The timeout stays; the work moves.
- **A heavy check has a budget.** Each check in the merge gate's pool stays under a per-check cap, and the pool under a total at the runner's job count, enforced by a test in the project. A check over its cap moves to the nightly run with a smoke twin (one seed, a short horizon, its invariants still gated) in the merge gate, or buys room by getting faster.
- **Check the clock before starting.** A run estimates its time from each check's recorded time before it starts, and refuses to start when the estimate is over 85% of its limit. Past 75% after it finishes, it warns, so the next one gets moved before it times out.
- **Never redo what passed.** A rerun of the same tree, after a timeout, a cancel, a runner death or a real failure, skips the steps and checks that already passed on it and says which run it took them from. Pass markers live outside the workspace, keyed by the tree's SHA, and expire after a few days.

The ready gate follows the same rule: when the full local check can't fit a single command's time limit, it runs in parts, and a summary step proves the parts ran on one tree, against the same `main`, and together passed every check.

*Why:* in the reference project, three merge-gate runs died on the timeout in five days (90, 121 and 120 minutes, the last after every check had passed), each followed by a full rerun: 331 minutes of the only runner. The first fix tried was raising the timeout, which only made the next death longer. The owner (2026-11-05): "i dont like the habit we have of wasting time on builds we know are not going to work."

## Habits that make any tier cheaper

- Keep PRs in draft while working; run the full local check before marking ready.
- Push as little as you can; squash fix-ups locally.
- A waiting run usually means the runner is busy, not off. The queue job's log says what it's waiting for.
- A PR that conflicts with `main` fails in the queue job at once, before building.
